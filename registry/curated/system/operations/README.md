# @framers/agentos-ext-operations

[![CI Status](https://github.com/framerslab/agentos-extensions/workflows/CI/badge.svg)](https://github.com/framerslab/agentos-extensions/actions)
[![npm version](https://img.shields.io/npm/v/@framers/agentos-ext-operations)](https://www.npmjs.com/package/@framers/agentos-ext-operations)
[![License: Apache 2.0](https://img.shields.io/badge/License-Apache_2.0-blue.svg)](https://opensource.org/licenses/Apache-2.0)

A product's operations records in its own database, through the SQL storage adapter it already passes: support requests a person opens from the app and staff work from the admin, a log table with search, an events table with daily totals over the product's own figures, and the jobs that keep them, every table under a prefix of the product's choosing. This release builds support requests (the thread, a per-request anonymous id, the live stream, mail and bell outboxes, pictures, deletions and the export), lines, events, the daily totals, the metrics hook, the `fields` rule and the migrations. Error capture and health checks share the same tables, migrations and rule: their tables exist from this release and their types are exported, and their functions come in the next minor release. Until then each of them throws `not_built` when it is called, never when it is imported.

```ts
import { createOperations, migrateOperations } from '@framers/agentos-ext-operations';

await migrateOperations(db, { prefix: 'ops' });

const operations = createOperations({ db, release: commit, process: 'web', locks: [701, 702, 703], alertsTo: 'team@example.com', logger, mail, routePattern, fields });
operations.start({ shared: true });

operations.lines.push({ process: 'web', kind: 'request', status: 200, path: '/api/notes/[id]', fields: { ms: 41 } });
operations.events.record('note_saved', { plan: 'plus' });

const failures = await operations.lines.search({ status: '5xx' });
const requests = await operations.events.metric('api_requests', 30);
```

## What this release holds

| Part | In this release |
|---|---|
| `migrateOperations` | Builds fifteen tables on PostgreSQL and SQLite under the product's prefix: the package's fourteen and their migration ledger, `<prefix>_schema_migrations`. |
| `operations.lines` | `push` checks a line against the `fields` rule and queues it; `search` finds lines by kind, path, status, process and time. |
| `operations.events` | `record` checks an event and queues it, its time cut to the hour; `metric`, `funnel`, `retention`, `money` and `today` read the figures; `fill` writes the daily totals of past days. |
| The metrics hook | The product's figures by day and plan, beside the package's own. |
| `start` and `stop` | The flushes in every process; in the process that runs the shared jobs, the nightly totals at 00:20 UTC and the hourly sweep of every retention. `stop()` ends the timers, writes the held `ops_refused` lines and flushes, twice within 3 seconds, so the lines a host logger pushes back are written too. Once it answers, nothing the package started begins a write: a statement still running goes on unawaited, a flush begins no further batch, a flush through an adapter without `batch()` begins no further row and a totals write no further statement, both rolling back whole, the shared jobs begin no further statement and write no beat, and what a queue still holds is let go and counted on one `ops_flush` line. |
| `operations.tickets` | Support requests, given the `tickets` module: the person's `open`, `list`, `get`, `read`, `write`, `share`, `resolve`, `remove`, `upload`, `picture` and `stream`; staff's `staffList`, `staffGet`, `reply`, `claim`, `setPriority`, `setState`, `openIdentity`, `writeTo`, `staffRemove` and `stats`; `systemMessage` for the product's own events; `hangup` for the product's account deletion step; `sendDue` and `notifyDue`, which drain the mail and bell outboxes. Null when `tickets` is left out. |
| `deleteAccount`, `exportAccount` | `deleteAccount(trx, accountId)` deletes every request of the account inside the product's own transaction; `exportAccount(accountId)` answers the account's requests and pictures as a zip stream, one export at a time and three a day. |
| `./react` | Headless hooks over the product's `fetch` for the person's and staff's pages and the composer, and `Markdown`, the sanitized renderer. |
| `operations.errors`, `operations.health` | Each function throws `not_built` at the call, naming the next minor release. |
| `./errors`, `./health`, `./http`, `./browser`, `./remote`, `./worker`, `ops-check` | Each entry imports, and each of its functions throws `not_built` at the call. |

A `not_built` error is an `Error` whose `code` is `not_built`, whose `surface` names what was called, and whose message says that it comes in the next minor release.

## Installation

```bash
npm install @framers/agentos-ext-operations @framers/sql-storage-adapter
```

It needs Node.js 22 or later. One dependency installs with it, `character-entities`: HTML's table of named character references, the one the renderer decodes a markdown destination with, which the link cut reads so that `&sol;sign-in` is cut as `/sign-in` is. Every other dependency is an optional peer: `@framers/sql-storage-adapter` (`>=0.7.15`) for the root entry, `./logs`, `./events` and `./tickets`; `sharp` (`>=0.35`) for pictures, loaded at the first upload; `react`, `react-markdown`, `remark-gfm` and `rehype-sanitize` for `./react`. `zod` is the peer of the next minor release's `./http`, and nothing in this release loads it.

## Adopting it in a new product

The steps below are what a product does to take this release. The steps of the full adoption that need the next minor release follow them.

1. **Install** `@framers/agentos-ext-operations` with `@framers/sql-storage-adapter` (`>=0.7.15`; a product on the adapter's 0.6 line moves to 0.7 as an increment of its own first). Pin exact versions.
2. **Migrate.** The product's migration command runs the package's tables first, then its own:

   ```ts
   import { migrateOperations } from '@framers/agentos-ext-operations';

   await migrateOperations(db, { prefix: 'ops' });
   ```

   The prefix is a lower-case letter followed by at most 32 lower-case letters, digits or underscores, so PostgreSQL's 63-byte names hold the longest index name whole; on SQLite, `sqlite` and a prefix beginning `sqlite_` are refused too, since SQLite keeps those names for itself. The prefix is written into every migration's checksum, so a product keeps its prefix for life. The migrations run under the ledger `<prefix>_schema_migrations` and the adapter runner's lock (724313571 unless `lockKey` names another), so the product's own runner and this one never apply at once. Run twice, the second applies nothing. The package's migrations only add, so an older release still starts against newer tables.
3. **Configure** one `Operations` a process, and start the shared jobs in one process alone. The shape for a product with figures of its own:

   ```ts
   const operations = createOperations({
     db,
     prefix: 'ops',
     release: commit,
     process: 'web',
     locks: [lockTick, lockSweep, lockTotals],
     alertsTo: 'team@example.com',
     logger,
     mail,
     routePattern,
     fields: {
       status: { kind: 'integer' },
       ms: { kind: 'integer' },
       kind: { kind: 'word', words: ['request', 'error', 'job'] },
       session: { kind: 'id' },
       path: { kind: 'path' },
     },
     metrics: { plans, metrics: { signups, minutes }, excluded },
   });
   operations.start({ shared: true });
   ```

   `locks` are three distinct integers, the tick's, the sweep's and the totals': on PostgreSQL each shared job runs in a transaction that first asks `pg_try_advisory_xact_lock` for its number, so a second process skips a run rather than waiting for it; on SQLite the locks are skipped. This release runs the sweep and the totals, and the tick comes with health. Every other process calls `operations.start({ shared: false })`, which runs its flushes alone; a later `start({ shared: true })` arms the shared jobs, and a later `start({ shared: false })` leaves them running. `logger` is any object with `info`, `warn` and `error` (AgentOS's `ILogger` is one). `routePattern(pathname)` answers the pattern of the product's route for a path, or null. `release`, `alertsTo` and `mail` are checked when the operations are created. With `tickets` given, `mail` sends the support mails (a reply left unread, an identity opening, and a new request's alert to `alertsTo`; Support requests below); `release` is read by the error capture of the next minor release. `limits` overrides the defaults below, and `now` gives the jobs and the written times a clock other than `Date.now`.

   The short shape, for a product with no figures of its own (a runtime, a worker, a command), leaves `metrics` out: the Analytics views answer the package's own figures alone. Leaving `tickets` out, as both shapes here do, makes `operations.tickets` null; the `tickets` module is described under Support requests below.
4. **Declare the fields** the product's log lines and events may carry, before any line is pushed: a closed list of keys, each an integer key, a word key with its words, an id key (32 hexadecimal characters) or `path`, which holds a route pattern that the product's `routePattern` answers with itself, or the word `unknown`. The package refuses every other key or value, a nested object and an array, and counts the refusals into one `ops_refused` line a key a minute through `logger`, naming a declared key or `unknown`, never the value. A declared key whose value is `undefined` is left out, as JSON leaves it out. A logger whose lines are free text pushes nothing until its lines are objects under this rule. A logger that pushes what it logs hands the package's own lines back too: one the rule refuses (its kind outside a declared `kind` rule's words, or a key the rule does not declare) is counted toward the next minute's `ops_refused` line, so that logger gets one `ops_refused` line a minute, never a burst. Declaring the own lines' kinds and their keys (`queue`, `written`, `refused`, `kept`, `dropped`, `key`, `count`, `job`, `step`, `metric`, `outcome`) stores them in the table instead.
5. **Push and record.** Hand each of the product's checked log lines to `operations.lines.push` and each event to `operations.events.record`. Neither throws nor waits: each queues, and the queue flushes every 5 seconds once `start()` has run, or at once at 500. A line's `kind`, `status` and `path` are columns, checked under the product's rule when it declares those keys (a value the rule admits must still fit its column: text for `kind` and `path`, a whole number for `status`), else as a word, an HTTP status and a route pattern, and its other fields go under the rule. An event's `plan` is one of the product's plan words (any word when `metrics` is left out) or `none`, its `n` a whole number of 0 or more, and its fields hold no id key, since an event names no one. Call `operations.stop()` from the server's `SIGTERM` listener, close the database after it answers, and give the container a stop grace long enough for its 3 seconds.
6. **Metrics.** Give each figure of the product's own as a function of the day's bounds and the excluded accounts, answering rows of `{ plan, value }` with the product's plan words, `none`, or `all` for a figure that splits by no plan. `all` is refused in `plans`, since the totals write the sum over the plans under it. A value is a number: PostgreSQL's driver answers `COUNT(*)` as a string, so the hook converts it.

   ```ts
   import type { OpsMetric } from '@framers/agentos-ext-operations';

   const signups: OpsMetric = async (db, dayStartMs, dayEndMs, excluded) => {
     const left = excluded.length === 0 ? '' : ` AND id NOT IN (${excluded.map(() => '?').join(', ')})`;
     const rows = await db.all<{ plan: string; value: number | string }>(
       `SELECT plan, COUNT(*) AS value FROM accounts WHERE created_at >= ? AND created_at < ?${left} GROUP BY plan`,
       [dayStartMs, dayEndMs, ...excluded],
     );
     return rows.map((row) => ({ plan: row.plan, value: Number(row.value) }));
   };
   ```

   A figure split by a second word (sessions ended by reason) is one metric a word, `<metric>_<word>`. An entry `{ count, losesDeleted: true }` marks a figure whose source loses deleted accounts, `{ count, fillsBack: false }` one whose source has no history before the landing, and `source` names where it comes from. `excluded(db)` answers the staff and test account ids the figures leave out. `funnel` names four metrics in order, and `retention(db, weekStartMs, excluded)` answers one sign-up week's cohort. The package reads its own figures from its tables and nothing from the product's.
7. **Fill.** Once, at the landing, call `operations.events.fill(90)` to write the totals of the last 90 days from every source that keeps its history: only the days and metrics with no row yet, the package's own figures from the day its tables were made, and no entry marked `fillsBack: false`.
8. **Read.** Call `operations.lines.search(query)` and the five views inside the product's own staff routes, after its own permission check: this release checks no permission itself. `OpsPermission` names the eight permissions of the full package, and `logs.read` and `analytics.read` are the two these reads map to.
9. **Privacy.** Say on the product's privacy page what this release keeps and for how long: a copy of the checked log lines for 14 days, events counted by hour and plan for 90 days, and daily totals for two years. None of them names a person.
10. **Tests.** Add the product's own end-to-end journey of a line pushed and found by search, and an event recorded and read back in the views after the nightly totals or a fill.

With the next minor release, the full adoption adds: the capture of route failures, `onRequestError`, `uncaughtExceptionMonitor`, `unhandledRejection` and browser failures; `./http`'s handlers mounted with the product's `person` and `staff`; health checks, the minute tick that drains the outboxes and the alert throttle; error records on the privacy page; `ops-check` on a second machine and `./worker` on an edge cron; and the tests of a failure.

## Support requests

`operations.tickets` exists when `createOperations` is given the `tickets` module: `identity(accountId, db)` (the account's name and address, `{ deleting: true }` while it is being deleted, or null; `db` is the handle to read the product's tables through: inside `open`, `writeTo` and `systemMessage` it is the package's write transaction, which holds one of the pool's connections while it asks under the account's lock, so a read through the pool there would wait on that transaction itself, inside an outbox's claim on PostgreSQL the claim's transaction, and elsewhere the adapter), `audit(trx, entry)` (the product's staff record, inside the package's transaction), `staffRecipients(db)` (the account ids told of a new request), `notify(notice, db)` (the product's notifications, optional; both, like the root's `mail(message, db)`, are given the handle to read the product's tables through: inside an outbox's claim on PostgreSQL the claim's transaction, elsewhere the adapter, so a hook that reads them never waits on the pool the claim holds a connection of; a hook that takes one parameter is unchanged), `categories` (2 to 12 words), `words` (the sentences the package itself renders: a system message from its key, an alert's lines, the export's labels), `tokenPaths` (the paths whose links are cut to the path before a subject or a body is stored, so a pasted sign-in link holds no token: an http or https address, a `www.` address with no scheme, and a relative markdown destination rooted at `/`, in a link or a reference definition, at the line's start or inside a blockquote or a list item, indented up to three spaces or not, each destination decoded as the renderer decodes it (a backslash escape, a numeric or a named character reference, `&sol;` included) before the cut decides what it is, with the markdown marks around the link kept; the text is cleaned of its control characters first, so one inside a path never hides the path from the cut) and `excluded(db)`. Each function takes its actor, so the product's own route calls it after its own permission check; a request that is not the person's answers `not_found`, never `forbidden`. A person is `{ accountId, plan }` and a staff member `{ accountId, role }`, as the product's auth answers them (`OpsPerson`, `OpsStaff`): the package tells the two apart by the word each carries, so an object carrying both `plan` and `role`, or neither, is refused (`refused`, 400; `not_found` from `picture`; nothing from a list) rather than read as the wrong one.

```ts
const opened = await operations.tickets.open(person, { category: 'billing', subject: 'Charged twice', body: 'My card was charged twice.' });
// Every call answers its value or an `OpsRefusal` (`{ refused, status, retryAfter? }`): here the quota, the cooldown, the hourly rate, or `not_found` for an account being deleted.
if ('refused' in opened) return new Response(opened.refused, { status: opened.status });
const stream = await operations.tickets.stream(person, opened.id, request.headers.get('Last-Event-ID') ?? undefined);
// stream.body is text/event-stream bytes; stream.headers the three headers to answer with; stream.close() ends it.
const reply = await operations.tickets.reply(staff, opened.id, { body: 'Refunded; it shows within five days.' });
```

- **The thread.** A request holds its anonymous id (`P-` and six characters, drawn for the request alone, so two requests of one person share nothing staff can see), its category, subject, priority, stored state (`open`, `resolved`, `closed`) and the derived state people read (`waiting_team`, `waiting_person`, `resolved`, `closed`). A message on a resolved request, the person's or a staff reply, reopens it with its `reopened` system message, so the close step never closes the thread under a question staff just asked; a closed one answers `409 ticket_closed`, and a closed request staff mark resolved keeps no close time. A subject and a body are checked as they are stored, with their control characters gone, so one of control characters alone is refused (`400 refused`). `systemMessage` records the product's own events under keys of its own: one of the package's keys (`OpsSystemMessageKey`: `identity_opened`, `reopened` and the rest) throws a `TypeError`, as a malformed key does, since the package writes those beside the changes that cause them. One person's quota, cooldown and hourly rate are checked one call at a time (an advisory lock on PostgreSQL), so a burst of calls lands what the limits allow, and a request's first message counts toward the hour's thirty. A request removed (`remove`, `staffRemove`) still counts toward the quota and the cooldown for a day, and the person's messages on it toward the hour, in the process that removed it, so open, remove, open is refused as open, open is; the tables keep no deleted row, so that memory is the process's alone (at most 10,000 accounts, the least recently remembered forgotten first): another process or a restart starts with nothing, and the account's deletion forgets it. Staff see the anonymous id and the plan until the person turns the share switch on for that request or a staff member with the product's identity permission opens the account, which is audited, written into the thread and told to the person by mail and by the bell whatever the request's state. Both lists page from the last request shown (the person's newest first; staff's urgent first, then the longest waiting on the team, then the id), so a request opened between two pages repeats nothing and hides nothing older. `open`, `writeTo` and `systemMessage` take the account's lock and then ask `identity()`: an account the directory does not know or marks `deleting` is refused `not_found` (`systemMessage` writes nothing and answers null), so a write that waited for a deletion in flight never lands after it; a lookup that throws fails no write and counts one `ops_identity` line (on PostgreSQL the lookup runs from a savepoint, so a statement the directory fails through the handle is undone and the write goes on, whether the directory throws or swallows the failure and answers). `reply`, `claim` and `writeTo` take the staff member's own lock too and read their liveness the same way (`writeTo` both accounts' locks, in one order), so a staff member whose account is being deleted writes nothing that names them: refused `not_found` once the deletion commits, and the `claimed_by` and `sender_account_id` the deletion cleared never come back. A link to one of the product's token paths is cut before the words are stored, in every spelling the renderer links: an address, a `www.` address with no scheme, or a relative markdown destination (bare or in angle brackets, after spaces or a line break, in a reference definition at the line's start, at any indentation, or inside a blockquote or a list item, its destination on the same line or the next whatever ended the line, a line feed, a carriage return and line feed or a carriage return alone, its label read as the renderer reads it with an escaped bracket or a line ending inside, with a backslash escape, a numeric or a named character reference or percent-encoding in its path), each read to its balanced end, so parentheses in balanced pairs (in a destination, escaped ones too) are part of the link, as the renderer reads them, and a token behind them in the query is cut with the rest; the destinations are cut before the addresses in running text, which read no escapes, so an escaped parenthesis in a destination never cuts it short. A destination kept as written is read again for the links inside it, since the renderer reads an opener that opens no link as text: the link in `]([login](/sign-in?token=<t>))` works, and is cut.
- **The stream.** `stream(actor, id, lastEventId)` answers `text/event-stream` bytes: `: open`, then one `state` event with the request's state as the connection finds it (its id and the cursor's time from one read, the row read after them; a claim, a priority or a state set while no stream was open writes no message, so only this event carries it to a page that reconnects), then one read at once, so a write that landed while the stream opened is sent now rather than at the next timed read, a `message` event a new message, a `state` event a change of the derived state, the claim or the priority, `: keep` every 25 seconds and `: end` when it closes, after 15 minutes at the latest; the page reconnects with `Last-Event-ID`. A write sends `pg_notify('<prefix>_tickets', <id>)` inside its transaction and one `listen()` a process wakes the request's streams; every stream also reads each 60 seconds, on SQLite every 5. On a PostgreSQL pool bounded to one connection (`max: 1`, read from the adapter's pool when the first stream opens) no listener is made, since it would hold the pool's only connection and the stream's first read would wait on it for ever: the streams read every 5 seconds instead, with one `ops_listen` line (`state: off`, `pool: 1`). Every event carries the newest message's id, a `state` event before any new message too, so a reconnect always has one to resume from. `stop()` ends every stream, and a stream asked for after it is refused `stream_busy`, so the page polls until the next process answers. An open still reading when `hangup` or `deleteAccount` ends the actor's account or the request's is refused `not_found` instead of registering, so no stream runs on for an account that is gone. A stream opens only for an actor the directory knows and does not mark `deleting`, on a request whose account it knows the same way (`not_found` otherwise), and every stream asks the directory about both every 60 seconds and ends when either is gone; `hangup` and `deleteAccount` send the account's end over the notice channel too (the deletion's at its commit), so the streams the account holds in every process end at once where a listener is up and within a minute where none is; a lookup that throws ends no stream and counts one `ops_identity` line.
- **Mail and the bell.** A staff reply is written `owed`; `sendDue(now)` mails it through `mail` as `supportReply` when the person has not read it five minutes later and the request has had no mail in 30 minutes, marks it `skipped` otherwise, tries a failed send once more, never mails an account the directory does not know or marks `deleting`, and leaves the row owed for the next tick when `identity` throws, reading on past such rows (a page at a time, ten pages at most) to the mail behind them, the next run starting after the last row this one read when it stopped at its page or batch bound and at the oldest row again once a run reaches the end, so rows whose lookup keeps throwing never starve the mail behind them. The identity opening's mail is owed the same way: sent at once by `openIdentity` when the directory answers a live account, skipped for one gone or deleting, and the tick's when the lookup throws or the send fails, with no five-minute wait and no gap. `get` and `read` mark the thread read up to the newest message they answered (the request's pointers and, for `get`, the messages it answered; never the clock), and `read(actor, id, messageId)` up to that message of the request alone (the page sends the id of the message it delivered; another request's message or none answers `not_found`), so a reply that lands after the thread was read, or after the message the page delivered, stays unread and is mailed; a marker never moves backwards, so an older read that finishes after a newer one leaves the newer marker. `notify` is called after each commit with a dedupe key from the message's id, to the recipients the directory knows and does not mark `deleting`; `notifyDue(now)` tries again for a minute-old unmarked row, three attempts in all, a `notify`, `staffRecipients` or `identity` call that throws counted as one of them. Each row is claimed before a hook is called for it, so two drains at once deliver each notice once: in a process the module holds the row's id while it is sent or rung, which the identity opening's at-once send and a run share, and one run of each outbox goes at a time (a call while one runs joins it); across processes, on PostgreSQL, the claim is a transaction that first asks `pg_try_advisory_xact_lock` for the row (the channel's and the message id's hashes) and reads the row's state again inside it, the hooks run inside it with `identity` given its handle, a reply's claim then takes the request's own lock and reads its pointers fresh (so two processes draining two replies of one request judge the gap in turn), and the row is marked through the same handle, so a row another process holds or has settled is passed over and counted nowhere, and the claim ends with the transaction, a dying process included; every hook inside the claim, `identity`, `staffRecipients`, `notify` and `mail`, is given the claim's handle to read the product's tables through, since a read through the pool there would wait on the claim's own connection (a pool of one never answers, and bells rung at once exhaust a wider one); on SQLite, one process by deployment, the in-process rule alone. The two drains claim through one key, the message's id, so a row whose mail is in flight is passed over by the bell drain with no attempt counted and rung at the next tick, and one whose bell is in flight is left owed for the next mail run: a minute's wait on an overlap, never a lost notice. A statement the database refuses inside one row's send or ring fails that row alone: on PostgreSQL a claim's hooks run from a savepoint the claim settles once they return, so a statement a hook fails is undone back to it and the claim's writes before it stay, whether the hook throws or swallows its own failed statement and answers (a bell's attempt stays counted, a mail hook's failure is counted as a failed send); a refused mark leaves the row owed for the next tick, counted deferred on the run's `ops_mail` line, and the run goes on to the rows behind it with its lines written whatever ends it, the identity opening's at-once send left owed the same way. Until the minute tick of the next minor release calls them, a product that wants the mails calls `sendDue` and `notifyDue` from a timer of its own. A new request's alert goes through `mail` as a `teamAlert` with the category and the request's id, never its words or the anonymous id, behind `open`'s answer: `open` answers once its write commits and the bell has rung, so a mail hook that is slow or never settles holds no answer, and a failed send keeps its `ops_mail` line. A staff view whose identity lookup throws shows the request with no identity, counted on one `ops_identity` line a page, so one account the directory cannot answer for fails no page and no write that landed.
- **Pictures.** `upload(actor, bytes, declaredType)` takes PNG, JPEG or WebP under 5 MB, checks the leading bytes against the declared type, decodes with sharp one at a time a process, and stores a WebP at most 2,000 pixels on its long side with no metadata; a person holds at most 20 uploads no message has named within the hour the sweep keeps them (`picturesUnattachedMax`), and the next is refused `429 upload_quota` with `retryAfter` before it is decoded, so one account fills no table and holds no decode (a picture a message names frees its place at once, and staff uploads are not counted); a person's upload lands under the account's lock with its liveness read fresh, as `open` does, so an account deleted while the decoder ran, or one the directory marks `deleting`, gets no picture row (`not_found`); a message's `pictureIds` attach the person's own uploads (staff's carry no uploader), and a request's first picture asks for `consent: { version }`, recorded on the request once; later pictures on that request ask for nothing. `picture(actor, id)` answers the bytes to the request's person or to staff; the product's route sets `PICTURE_HEADERS` (exported by `@framers/agentos-ext-operations/tickets`: `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'`, `Cache-Control: no-store`) on the answer. A decoder that cannot be loaded (sharp missing or broken) is thrown to the caller as `PictureDecoderUnavailable`, never answered as `not_an_image`, and is tried again at the next upload.
- **Deletion and export.** `remove` and `staffRemove` delete one request with its messages, pictures and owed rows and end its streams, under the request's account's lock, so a write of the person's that holds it lands first and its message goes with the rows and is remembered for the hour's rate as a kept one would be (two removals of one request at once delete it once: the one that finds the rows gone answers `not_found`, remembers nothing of it for the quota and writes no line or audit entry); `deleteAccount(trx, accountId)` does the same for every request of the account inside the product's transaction, under the account's lock (so an open in flight commits first and its request goes with the rest), and nulls the account where a message or a claim names it; `hangup(accountId)` marks the owed rows skipped and ends the streams first. `exportAccount(accountId)` streams a zip holding `requests.json` and `pictures/<request id>/<picture id>.webp`; a second export at once or a fourth in a day throws `OpsRefused` with `export_quota`.
- **`./react`.** `useRequests`, `useRequest`, `useStream` (reading the stream's lines however they end, a line feed, a carriage return or the pair, a pair split across two chunks included; reconnecting with `Last-Event-ID` when a stream ends, waiting twice as long after each failed connection up to a minute, stopping with `mode: 'closed'` and the refusal's word on a refusal the server will keep giving (a 4xx other than 408 and 429), handing an event to `onEvent` only while the page is visible, the events that arrive behind a hidden page held and handed on in order when it shows again (a newer `state` replacing the one held before it, and a new connection for the same request, as a change of client or of an option makes, asking the server for the held events again from the last event handed on), so a page that calls `useRequest`'s `refresh()` from `onEvent` (its read marks the thread read; an event already carries the message to append) never marks read a reply nobody saw, marking the newest message handed on read through `POST .../read` with `{ messageId }`, which the product's route hands to `read`, so a reply the person watched arriving, or saw on coming back to the page, is never mailed, polling every 20 seconds after `stream_busy` while the page is visible, since the page's read marks the thread read and a reply behind a hidden page is mailed), `useComposer` (the body under 5,000 characters, Write and Preview, templates by category, up to 3 pictures), `useStaffList` (reading `GET <base>` with the filter as its query, with no slash before the query or after the base, as a router that matches paths strictly serves it) and `useStaffRequest`, each over an `OpsClient` of the product's `fetch`, the base path of its routes and, when one `fetch` serves every session, a `session` word (the account's or the session's id) that changes with the sign-in; a reading hook shows nothing of the request, or of the client, the page left while the next one loads (what was read belongs to the client, its `fetch`, its base and its `session` word, and the path, so another account's session under the same routes, behind the same cookie-bearing `fetch` too, sees none of the first's requests), a `refresh` kept past the unmount reads nothing, and the stream hook ends its stream and connects again when the client changes, and `readJson` keeps the caller's headers in any form, reads a 2xx body that is not JSON as `failed` and a 204 as `data: null`; and `Markdown`, which renders a body with no raw HTML, no images and every link `rel="noopener noreferrer nofollow ugc"`.

## Lines and the search

`lines.push({ process, kind, status?, path?, fields? })` keeps one line shape (process, kind, status, path) at most 60 times a minute; past that it counts the lines and writes one `ops_rate_cut` line with the count at the minute's end in their place, and the request figures add the counts back. A minute tracks 10,000 shapes; the lines of every shape first seen past them share one tally under the same limit, whose `ops_rate_cut` line names the process the package runs in and carries the count alone, so the request figures leave that count out. `lines.search({ kind, path, status, process, from, to, cursor })` matches `kind` exactly (one or several, at most 20; a longer list throws a `RangeError`), `path` as a prefix and `status` as one code or a class from `2xx` to `5xx`, over the last hour unless `from` and `to` say otherwise, 14 days at most (an older `from` is cut to 14 days), newest first, 100 lines a page, with a cursor of time and id for the next page. Pass `from` and `to` with the cursor, since the default window moves between calls.

## Events and the figures

`events.record(kind, { plan, n, fields })` writes one row to the events table with its time cut to the UTC hour. The nightly totals at 00:20 UTC write the day before into the daily table, one row a metric and plan with `all` as their sum; each metric counted replaces its rows of that day, so a run repeated writes the same rows; today's figures are counted live by the same functions. A hook that throws for one metric writes one `ops_job` line naming the metric, and the rest land. A process that is down at 00:20 UTC writes no row for that day: the `ops_totals` beat shows the gap, and `fill` writes the missing days.

The package's own figures: `api_requests` and `api_errors` (the product's log lines of kind `request`, and those that answered 5xx), `errors` with `errors_server` and `errors_browser`, `requests_opened` and `requests_open`. The error figures read the tables the next minor release fills, and count 0 until then.

| View | Answers |
|---|---|
| `metric(name, 30 \| 90)` | One metric's days by plan, its source (`own` or `host`), the source's name and whether it loses deleted accounts. |
| `funnel(30 \| 90)` | The four steps of `metrics.funnel` by week. |
| `retention(30 \| 90)` | Each sign-up week's cohort from `metrics.retention`, a week not yet over as null; nothing of it is stored. |
| `money(30 \| 90)` | The product's `purchase_amount`, `topup_amount` and `cost` metrics by day, in its micro units. |
| `today()` | The home row's counts: requests waiting, error groups first seen today, checks failing, sign-ups today and requests resolved today. |

## The shared jobs

| Job | When | What |
|---|---|---|
| `ops_totals` | 00:20 UTC | The day before's totals, under the totals lock. |
| `ops_sweep` | 40 minutes past each hour | First the requests' states: an open request whose latest message is staff's is resolved after seven days of the person's silence, and so is one the product opened with system messages alone (no staff message and no person message) seven days after its newest system message, since nothing else would end it; a resolved request is closed 30 days after it was resolved, each with its system message (`resolved_by_silence`, `closed`), the change written only while the rule still holds, so a message that lands between the read and the write leaves the request as it is. Then every retention below, at most 1,000 rows a statement until a statement removes fewer, each statement in a transaction of its own that first tries the sweep lock. A step whose statement fails writes one `ops_job` line naming it and the rest still run. |

Each job writes its beat to the beats table after each run (`ok`, `failed` or `skipped`, with the time of its last run that landed whole), so a stalled job shows. A run still going when `stop()` answers begins no further statement, inside a batch too, and writes no beat; a batch or a totals write it cuts short rolls back whole; `fill` writes a day whose totals it left unwritten. The sweep runs whenever the tables exist, whatever the product's own switches say.

## Limits

| Limit | Default | What it bounds |
|---|---|---|
| `lineQueue` | 5,000 | Lines waiting for a flush; past it the oldest go and are counted on one `ops_flush` line. |
| `eventQueue` | 5,000 | Events waiting for a flush, the same way. |
| `lineShapePerMinute` | 60 | Lines of one shape kept a minute before the rate cut. |
| `captureQueue`, `beatQueue`, `occurrenceEveryMs`, `browserGroupsPerDay` | 2,000, 500, 10,000, 500 | The error capture and the beats of the next minor release. |
| `ticketsPerDay`, `ticketCooldownMs`, `messagesPerHour`, `subjectMax`, `bodyMax`, `picturesPerMessage`, `picturesPerTicket` | 5, 30,000, 30, 200, 5,000, 3, 10 | Requests a person opens in 24 hours and the milliseconds between two (30 s), messages an hour across requests, the subject's and body's characters, pictures a message and a request (`429 ticket_quota`, `ticket_cooldown`, `message_quota` with `retryAfter`; `409 too_many_pictures`). |
| `streamsPerAccount`, `streamsPerProcess`, `streamLifeMs` | 3, 50, 900,000 | Streams an account and a process hold at once (`503 stream_busy` past either, and after `stop()`), and a stream's life before the page reconnects. |
| `pictureBytesMax`, `pictureInputPixelsMax`, `pictureLongSideMax`, `pictureOutputBytesMax`, `pictureWaitMs` | 5,242,880, 50,000,000, 2,000, 1,048,576, 10,000 | An upload's bytes (`413 too_large`), its pixels (`415 not_an_image` past them), the stored WebP's long side and bytes (at most 1,048,576, the bytes the attachments table takes for one picture; a higher `pictureOutputBytesMax` is refused at `createOperations`), and how long a second upload waits for the process's one decode (`503 busy`). |
| `picturesUnattachedMax` | 20 | A person's uploads no message has named, within the hour the sweep keeps them (`429 upload_quota` with `retryAfter`, read before the decode); a picture a message names frees its place, and staff uploads are not counted. |
| `mailUnreadMs`, `mailGapMs`, `exportsPerDay` | 300,000, 1,800,000, 3 | How long a staff reply stays unread before it is mailed, the least time between two mails on one request, and exports an account takes a day (`429 export_quota`). |

A batch that fails whole while the database is away goes back in front of its queue for the next flush; a row the database refuses alone is lost alone and counted. Every limit is checked when the operations are created: an unknown key or a value that is not a whole number of 0 or more throws a `TypeError` naming it.

## Privacy

| Table | Holds | Kept |
|---|---|---|
| `<prefix>_log_lines` | The checked lines; an id only under a key the rule declares as one. | 14 days |
| `<prefix>_events` | A kind, a plan, a count and fields of words and integers, the time cut to the hour; no id. | 90 days |
| `<prefix>_daily` | Daily totals by metric and plan. | Two years |
| `<prefix>_beats` | Each shared job's last run and outcome. | Current |
| `<prefix>_tickets`, `<prefix>_messages` | A person's requests and messages, their account's id, each request's anonymous id, the plan at opening, staff's replies; the name and address are read from the product at view time and never copied in. | A year after the request closed, or at once when the person or staff delete the request, or with the account. |
| `<prefix>_attachments` | Pictures decoded and written again as WebP with no metadata; the uploader's account id for a person's own upload, none for staff's. | 90 days after their request closed; an unattached upload an hour; at once with the request or the account. |
| The error and health tables | Nothing in this release. | Their retentions already run: an error group 90 days after it was last seen; occurrences 30 days; health samples 14 days; outages two years. |

The package's own lines (`ops_flush`, `ops_job`, `ops_refused`, `ops_rate_cut`, `ops_mail`, `ops_listen`, `ops_identity`, `ops_request_deleted`, `ops_export` in this release) carry a fixed word with words and integers, never a sentence and never an id.

## Tests

The suite runs every case on SQLite through sql.js in memory and, when `AGENTOS_TEST_POSTGRES_URL` names a server, on PostgreSQL; without it the PostgreSQL half shows as skipped under its reason. The repository's CI runs both, PostgreSQL 16 among its services. Fixture tests feed an address, a sentence, a token, a sign-in link and an error's sentence through every entry this release builds and find none of them in a table outside the support tables or in the package's own lines.
